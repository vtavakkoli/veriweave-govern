# Human evaluation protocol

Use this protocol to collect real validation without fabricating human results.

## Publication validation set

`research/validation/` contains six reviewable 25-case CSV partitions (150 total,
50 per domain) for regulation-grounded candidate cases:

- 50 public-administration actions;
- 50 enterprise IT / DevOps actions;
- 50 data-handling / AI-governance actions.

The master set contains provisional researcher labels and rationales. Those
fields are benchmark-construction hypotheses, not human ground truth and not
legal advice.

Two blind worksheets are generated by the first publication run:

- `results/publication/annotator-a.csv`
- `results/publication/annotator-b.csv`

They intentionally omit `provisional_label`, `provisional_rationale`,
`prohibition_reason`, system predictions and the other annotator's answers.

## Eligibility and independence

Use two genuinely independent annotators. For a publication-quality validation,
annotators should have documented familiarity with at least one relevant area:
EU/Austrian public administration, privacy/data protection, AI governance,
enterprise security/architecture, or IT/DevOps risk. Record only a pseudonymous
annotator identifier in the research artifact; do not commit unnecessary
personal data.

Annotators must not discuss individual cases, provisional labels, model outputs
or each other's decisions before both worksheets are frozen. They should work
from the same source snapshot and decision rubric.

## Decision rubric

Each annotator independently records:

- `decision`: exactly `allow`, `review` or `deny`;
- `confidence_1_to_5`: 1 (low) through 5 (high);
- `notes`: optional short rationale or ambiguity note.

Benchmark semantics are:

- **allow** — the described action may proceed under the supplied facts and
  evidence;
- **review** — accountable human/legal/privacy/security/governance assessment or
  additional evidence is required before execution;
- **deny** — the action as stated should not proceed because it matches a
  prohibition or an explicitly unacceptable disclosure/security condition.

These labels are operational governance decisions, not a universal legal
classification. Annotators should use the case's `evaluation_date`,
`legal_status`, official-source summaries and source links. Future-effective
cases must be assessed at their stated future evaluation date rather than the
repository snapshot date.

## Procedure

1. Run `make publication` once to generate both blind sheets.
2. Freeze the generated input sheets and source registry version used for the
   study.
3. Give annotator A only `annotator-a.csv` and annotator B only
   `annotator-b.csv`.
4. Each annotator reviews all 150 cases independently.
5. Validate that both worksheets contain exactly the same 150 case IDs and only
   valid decisions.
6. Compute raw agreement and Cohen's kappa **before adjudication**. Do not report
   a final kappa from a partially completed worksheet.
7. Create an adjudication meeting/package containing only cases on which the two
   annotators disagree, plus any cases explicitly flagged as uncertain.
8. Record the resolved label, a short rationale, a pseudonymous adjudicator ID
   and adjudication date in `results/publication/adjudication.csv`.
9. Preserve the original independent worksheets unchanged.
10. Re-run the publication evaluation. Use adjudicated labels as the evaluation
    target only when all 150 adjudications are complete.

If an annotator changes an answer after seeing the other annotator's decision,
retain the original independent answer for Cohen's kappa and treat the revised
answer as part of adjudication rather than silently replacing the original.

## Reporting

At minimum report:

- 150 total cases and 50 per domain;
- annotator expertise criteria and independence procedure;
- source-snapshot date and legal timing protocol;
- raw agreement;
- Cohen's kappa before adjudication;
- number and percentage of disagreements;
- number of adjudicated cases;
- class distribution of the adjudicated ground truth;
- VeriWeave and baseline accuracy, macro-F1 and false-allow rate overall and per
  domain;
- external-baseline availability/failure counts;
- limitations of researcher-authored scenario construction.

Until all required human labels exist, reports remain explicitly marked
`provisional-regulation-grounded` / **DRAFT — HUMAN VALIDATION REQUIRED** and
must not be described as human validated.

## Broader practitioner study

For a separate human-factors study, recruit practitioners across AI governance,
security/architecture, compliance/risk and software engineering. Recommended
conditions are human-only; human + VeriWeave decision trace/certificate; and an
optional actual LLM advisory condition.

Measure decision (`allow|review|deny`), duration, confidence (1–5), explanation
usefulness, missed violations and inter-rater agreement. Do not silently
substitute the deterministic language-style proxy for an LLM study.

The original long-format scorer remains available:

```bash
python -m research.human_eval research/human-annotations.csv
```

It reports annotation count, mean duration/confidence and mean pairwise Cohen's
kappa.

## Data protection and ethics

Use sanitized, synthetic or regulation-grounded constructed cases unless an
approved study protocol permits real organizational data. Never place citizen,
patient, employee, client-secret or other protected data in the public
repository. Do not publish annotator personal data without an appropriate basis
and study protocol.

If the study collects personal data, employment information, identifiable
expert opinions, or other human-subject data beyond the minimal pseudonymous
annotation records, follow the applicable institutional ethics/data-protection
process before collection.
